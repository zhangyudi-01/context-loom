# Workflow And Rules

## 0. 固定工作区布局

新建时将 `<module-root>` 作为模块工作区，将所有前置分析产物写入它的唯一直接子目录 `<module-root>/preanalysis/`。`preanalysis-manifest.json` 必须位于该目录，写入 `module_root=..` 和默认 `output.test_points_dir=../test-points`。不要把 README、需求包、Context Pack、RSU map、问题清单、Context Card 或 Data Closure 平铺到模块根目录。

该布局保留原测试工作流的下游发现协议：消费端接收 `<module-root>`，从根目录及直接子目录查找唯一 manifest。Context Loom 当前的 `loom-test-points` 支持此发现方式，但试运行结果写在用户指定的项目外隔离目录，不自动写入 manifest 指定的生产输出目录；详见 [交接契约](context-loom-handoff.md)。既有平铺或自定义布局可兼容维护，但不得在未获用户授权时自动迁移；新建或重建必须使用规范目录。

## 1. 盘点与只读探索

先递归读取模块目录，不要从空白模板覆盖已有人工答案或用户修改。至少确认：

- 模块需求包和它在需求全文中的位置。
- 项目全局上下文和资料注册表。
- 当前模块引用的附件、原型、接口、数据库、配置、环境和历史 PRD。
- 数据库相关模块的 schema、建表 SQL、关键查询、代码实体/Mapper、数据字典或经确认的数据库设计；缺一类时明确证据边界，不按命名猜关系。
- 现有 README、Context Pack、RSU map、问题清单和全部 Context Card。
- 用户明确排除的文件。

先建立来源清单，再开始写产物。来源清单至少标注：资源 ID、文件路径、语义用途、权威级别、是否进入当前范围、是否可机读。

同时读取或创建 `preanalysis-manifest.json`。manifest 只负责路径和资源角色路由，不保存业务结论；所有路径相对 manifest，禁止写本机绝对路径。

## 2. 先形成模块逻辑

不要一上来拆 RSU。先将需求全文、模块需求和用户讲解放在一起探索，回答：

1. 模块在整个项目中承担什么职责。
2. 用户通过该模块获得什么能力。
3. 当前新增或修改的部分是什么。
4. 哪些既有系统、任务、接口或文件规则只是被调用和沿用。
5. 从用户动作到最终可观察结果的完整主链路是什么。
6. 有哪些分支、失败边界、数据流、时间流和外部系统关系。
7. 本次验证到什么层级，哪些内容明确不重测。

把确认后的答案写入 `01-context-pack.md`。用户在探索前讲解的真实业务链路不能降级为“聊天补充”，也不能只散落在 Q 或 FC 中。

主链路优先使用简洁文本图：

```text
用户动作
  -> 页面/接口参数
  -> 后端或既有任务
  -> 中间系统
  -> 最终结果或验收位置
```

只有图能减少歧义时才增加 Mermaid；不要为了形式重复已有链路。

## 3. 处理资料冲突与范围

遵循以下规则：

- 当前需求决定本次新增页面或接口行为。
- 人工确认决定实际运行链路、沿用关系和本次测试边界。
- 历史 PRD 只提供已确认继续沿用的既有契约。
- 当前需求引用附件不等于附件全部内容自动进入测试范围。
- 范围裁剪按最小可定位章节或规则进行：可以排除附件的数据字段，同时纳入同一附件中的文件类型、数量、命名、目录或覆盖规则；禁止整文件一刀切。
- 页面提示、任务执行成功、中间文件存在和下游接收成功不是同一个结论，必须拆清证据层次。

出现冲突或不确定时，创建普通 `Q-ID`。权限、L2/L3、审计日志、失败反馈等范围疑问也使用同一问题清单；不需要强制 PM/开发签字或增加独立审批类型。

问题回答后：

- 更新 `03-clarification-questions.md` 的状态、结论和回填结果。
- 将模块级结论回填 `01-context-pack.md`。
- 将局部链路、契约或验证位置回填相关 FC。
- 只更新 RSU 的问题关联或状态，不改写 RSU 原文。

## 4. 建立 RSU 原文映射

`RSU` 表示 Requirement Source Unit。它是来源结构中能够独立表达一个完整业务契约的最小来源单元，不是 AI 重新表达的原子断言，也不是 Markdown 行、句子碎片、字段名或测试项。

本步骤必须完整读取 [RSU 语义拆分协议](./rsu-semantic-partitioning.md)，并严格分两遍处理。禁止一边遍历 Markdown 行，一边直接创建 RSU。

### 第一遍：建立原文结构与拆分决策

先按来源标题、编号、父子列表、表格和附件条款建立语义结构，再将每个进入范围的来源范围分类：

- `visual-placeholder`：原型标题、图片或附件占位符，本身没有文本行为。
- `structural-container`：只负责引出子项的容器文字。
- `field-fragment`：离开父级后不能独立理解的字段名、枚举项或结果项。
- `independent-contract`：自身包含对象以及条件、动作、限制或结果的完整条款。
- `composite-contract`：父规则与全部子项共同定义一个对象或结果契约。
- `unresolved`：现有资料不足以判断边界。

将判断写入 map 的 `原文结构与拆分决策` 表。处理决定只能是：

- `one-rsu`：该范围恰好形成一个完整 RSU；若同一行范围实际包含多个独立契约，先拆成多条来源范围。
- `not-rsu`：来源范围存在，但只作为视觉入口、结构上下文或其他 RSU 的组成部分。
- `pending`：缺少资料或上下文，暂不能判断。

不生成 RSU 的来源范围不能静默忽略；必须通过该表和来源覆盖表保留追溯。

### 第二遍：执行语义闭合检查

只对 `one-rsu` 范围创建 RSU。创建前逐个回答：

1. 这一单元约束的对象、字段、结果或操作是什么。
2. 适用条件、触发动作、状态或范围是否完整。
3. 行为、限制、枚举或可观察结果是否完整。
4. 是否仍依赖父级或兄弟项才能理解。

若第 1～3 项无法回答，或第 4 项为“是”，不得把当前片段单独建立 RSU。只将理解当前条款所需的最小原文条件/触发/状态/范围写入 `父级条件（原文）`，或把父规则和必要子项合并为一个 `composite-contract` RSU。父级中的动作和可观察结果不能只停留在父级条件列。

完成初稿后反向扫描全部 `父级条件（原文）`：凡包含创建/生成、修改/删除、写入/发送、状态变化、页面进入/跳转、弹窗/提示、展示等可独立观察行为的父级文字，必须在至少一个 RSU 的 `原文内容` 中完整出现。若没有，拆分尚未闭合，不得进入下游。

### 拆分依据

来源结构是语义分析的边界线索，不是“一条编号等于一个 RSU”的硬规则。优先识别：

- 编号规则及其子规则。
- 表格中的一行或一项。
- 有父级条件的步骤或结果。
- 当前需求明确引用且进入范围的附件条款。
- 经人工确认继续沿用的历史契约条款。
- 全局共享规则中确实约束当前模块的条款。

应用以下判断：

- 独立控件条款分别包含控件类型、选项、输入限制、选择方式或默认值时，可以分别建立 RSU；共同的 `查询条件包括：` 只进入其 `父级条件（原文）`。
- 父规则定义查询结果、排序或分页，子项只枚举结果字段时，父规则和完整字段列表合并成一个 RSU。
- 父规则只写 `任务列表的行内操作：`，子项分别包含状态条件和动作时，父规则不建立 RSU，完整子项分别建立 RSU。
- 父规则本身已经描述完整动作或结果、子项又补充其他可独立观察结果时，父规则和各完整子项分别建立 RSU；子项只继承最小条件片段。若子项只是字段碎片，则父规则与完整子项合并为一个复合 RSU。
- `原型`、`图片`、`附件` 等占位文字不单独建立 RSU；无法读取但确实影响验证时创建普通问题并标记来源覆盖状态。
- `任务 ID；`、`彩票年；`、单个枚举成员等字段碎片不得单独建立 RSU。

不要按句号、分号、冒号、换行或最小编号项机械拆分。一个来源句子可以作为一个 RSU；父句与多个子句也可以共同成为一个 RSU；多个不同来源契约仍可在后续形成跨 RSU 测试点。

### 原文保真

允许的规范化仅包括：

- 去掉 Markdown 链接的目标地址，保留可见文字。
- 合并普通空白和不换行空格。
- 将来源中明确的父级条件移到 `父级条件（原文）` 列。
- 将原本分行展示的复合契约按来源顺序连接为同一表格单元，但不得删减父句或子项。
- 为表格转义必要的竖线，不改变可见文字。

不允许：

- 改写成“应当”“必须验证”等测试断言。
- 补入人工确认、验证步骤、实现推测或范围结论。
- 为了“更原子”拆掉来源中不可独立理解的条件与结果。
- 为了减少数量提前合并不同来源条款。
- 把 `业务规则 1`、`规则 2.1` 等来源编号写进 `父级条件（原文）`；编号只属于 `来源定位`。
- 在 RSU 表中增加 `测试项`、测试意图、预期结果或验证步骤列。

### 防遗漏

完成 RSU 后必须建立“原文来源覆盖检查”表。首列使用 `SRC-ID > 章节/规则/字段范围`，按来源自身的标题、编号规则、表格或条款逐项登记：

- `mapped`：已映射为 RSU。
- `indexed-only`：保留引用入口，但不加载正文参与当前生成。
- `scope-excluded`：已明确排除。
- `pending-context`：原文已保留，但缺少可解释上下文。
- `pending`：资料不可读或尚未确认。
- `not-applicable`：已核实与当前模块无关。
- `not-rsu`：来源范围已审查，但属于视觉占位符、结构容器或已合并到其他 RSU 的字段碎片，不单独建立 RSU。

覆盖表是拆分后的防遗漏复核，不是单个 RSU 的动态输入，也不保存验证步骤。`not-rsu` 行应说明其语义角色以及由哪个 RSU 吸收；纯视觉占位符没有吸收 RSU 时写 `无` 并关联必要问题。同一附件允许同时存在 `mapped` 和 `scope-excluded` 行，但必须指向不同的明确范围；不得用“整份附件 indexed-only”掩盖其中已进入当前测试层级的文件级契约。

拆分决策表和覆盖表使用完全相同的 `SRC-ID > 语义范围` 作为对账键：`one-rsu` 必须对应 `mapped` 且 RSU 引用一致，`not-rsu` 必须对应 `not-rsu`，`pending` 必须对应 `pending` 或 `pending-context` 并关联状态为 `pending`/`deferred` 的 `Q-ID`。覆盖表中的 `mapped`、`not-rsu`、`pending`、`pending-context` 行也必须能反查到拆分决策；`indexed-only`、`scope-excluded`、`not-applicable` 可只存在于覆盖表。

## 5. 建立稳定索引

每个主产物顶部维护可点击资源表或快速索引。使用如下模式：

```markdown
| 资源 ID | 可点击文件 | 定位用途 |
|---|---|---|
| SRC-MOD | [当前模块需求](./00-module-requirement-pack.md) | 业务规则 1～3 |
| SRC-GLOBAL | [项目全局上下文](../../../../00-global/00-project-context.md) | 项目定位和共享术语 |
| CTX | [模块 Context Pack](./01-context-pack.md) | 模块背景、能力、详细逻辑和边界 |
| Q-INDEX | [问题确认清单](./03-clarification-questions.md) | 问题、回答和状态 |
| FC-001 | [功能链路](./context-cards/FC-001-功能链路.md) | 页面到外部任务的传递关系 |
| DC-INDEX | [Data Closures](./data-closures/README.md) | 数据闭包索引和状态 |
| DC-001 | [业务数据路径](./data-closures/DC-001-业务数据路径.md) | 表角色、连接/过滤、准备、查询和清理契约 |
```

索引规则：

- 表格行只写资源 ID 和“章节/规则/字段名”等语义定位。
- 不重复写长相对路径。
- 不为同文件 RSU、Q 或 FC 创建深层锚点。
- 文件名发生变化时统一更新顶部索引，并运行链接校验。
- ID 只能定位资源；后续生成前必须解析链接并读取实际正文。

## 6. 问题确认清单

统一使用两张表：已确认问题与待确认问题。不要临时改变列名或为每个模块发明新状态。

问题必须具体、可回答，并说明未确认时如何处理。常见来源包括：

- 时间基准、默认值和边界。
- 调用的是新逻辑还是既有服务。
- 外部文件、接口、数据库或 SFTP 的权威来源。
- 页面提示是否代表最终成功。
- 验证深度、权限、审计、失败反馈等范围疑问。
- 不可读取的原型图或附件内容。

如果问题仅涉及验证方法，回填验证位置 FC；如果仅涉及范围，回填 Context Pack 边界；如果形成需求原文之外的补充行为，后续测试点同时引用 RSU 和 Q。

## 7. Context Card

仅在以下内容会被多个 RSU 共同使用时创建 FC：

- 跨页面、后端、任务和外部系统的功能链路。
- 既有文件、接口、数据库或协议契约。
- 多层验收证据和观察位置。
- 需要集中维护的复杂条件或数据依赖。

每张卡固定包含：

1. `## 引用入口`
2. `## 定位`
3. `## 关联来源`
4. 一个或多个主题内容章节
5. `## 当前边界`

不要每个 RSU 建卡。不要让卡片复制完整 Context Pack，也不要把候选推测写成已确认事实。

## 8. Data Closure

数据库相关能力不能只登记“数据库设计文件”或画一张表关系图。先判断被测行为需要哪条业务数据路径，再按路径创建可复用 `DC-ID`：

1. 从需求、接口、SQL、代码和 schema 确定输入、输出及被测读写边界。
2. 列出路径内每张物理表的角色、主键/自然键、关键字段、访问模式和数据所有权。
3. 写完整 Join Predicate、基数和附加过滤；特别核对来源类型、业务类型、删除状态、租户/中心、时间和状态枚举。
4. 明确并集、去重、排序、聚合、空结果和一对多展开规则。
5. 为正常、边界、空数据、断链、重复/覆盖等必要状态定义 `DP-ID`，说明可重复准备、动态预期推导和清理策略。
6. 将闭包绑定到实际依赖它的 RSU，不把所有模块 RSU 默认挂到同一张巨图。

状态判定：

- `ready`：结构和语义足以支持测试点及可执行用例设计。
- `test-point-ready`：测试点语义已闭合，但环境 SQL、造数或清理仍有明确输入缺口。
- `blocked`：缺口会改变测试点本身，关联 RSU 必须停止并通过普通 `Q-ID` 澄清。

数据闭包粒度介于“模块整库图”和“每 TP 一图”之间。后续候选及最终 TP 单独记录 `Data Closure Refs`，正式用例再基于 DC 的 Profile 实例化查询、造数和清理 SQL。

## 9. 后续逐 RSU 生成契约

每次生成任务必须自包含，不依赖上一轮对话已经读取过资料。

固定输入：

1. 全局项目上下文全文。
2. 当前模块需求全文。
3. Context Pack 中的背景、能力、已确认详细逻辑和理解边界。
4. 当前 RSU 完整映射行。

动态输入：

- 当前来源定位指向的真实片段。
- 相关 Q 的答案和状态。
- 相关 FC 和 DC 的实际内容；卡片必须完整保存测试点阶段需要的聚焦语义。
- 当前 RSU 需要的附件、API、数据库、配置和环境资料。
- 确实需要的其他 RSU 及其动态依赖。

FC/DC 卡中的引用入口、依据资源和关联 RSU 是追溯关系，不自动递归加载来源全文，也不让当前 RSU 继承其他 RSU 的全部动态依赖。下游为这类证据记录路径、用途和正文哈希，以便审计和检测变化；只有当前 RSU 的“相关上下文”显式列出的资源才加载实际正文。确需长来源中的具体条款时，建立聚焦资源并给出语义定位，或补全 FC/DC 后再交付。

`indexed-only` 和 `scope-excluded` 只保留追溯，不加载正文。资源 ID、链接和语义定位不能替代当前 RSU 明确需要的实际内容，也不能成为递归投喂整份附件的理由。

后续每个正式测试点至少记录：

- `primary_rsu_id`
- `source_rsu_ids`
- `question_refs`
- `context_refs`
- `data_closure_refs`（涉及数据库时；不涉及时为 `无`）

逐 RSU 生成结束后，再统一执行去重、覆盖、引用完整性和跨 RSU 组合检查。

## 10. 固定排版

严格使用 `references/output-contract.md` 中的章节顺序和表头：

- 不修改列名同义词。
- 不随意增加或删除主章节。
- 领域特有内容放入规定的可扩展章节，不另造一套文件结构。
- 使用一个空行分隔标题、正文、表格和代码块。
- 表格列数必须稳定，空值使用 `无`，不要留空单元格。
- ID 使用三位数字：`RSU-001`、`Q-001`、`FC-001`、`DC-001`。
- 中文列举多个 ID 使用 `、`，连续范围可使用 `～`。

## 11. 强校验与完成条件

执行前先解析当前 `SKILL.md` 所在目录为 `<skill-dir>`，然后运行：

```bash
python <skill-dir>/scripts/validate_preanalysis.py <module-root>/preanalysis --require-canonical-layout
```

审核尚未迁移的既有平铺或自定义布局时可以省略 `--require-canonical-layout`，但必须保留并报告布局兼容警告。

只有以下条件全部满足才可报告完成：

- 必需文件存在，章节顺序和表头正确。
- `preanalysis/v1` manifest 的模块根目录、产物角色、固定资源角色和输出目录可解析且没有越界。
- 新建产物位于模块根目录的直接子目录 `preanalysis/`，下游能从模块根目录自动发现唯一 manifest。
- 无模板占位符。
- 全部本地链接可解析。
- 资源、RSU、Q、FC ID 唯一且引用闭合。
- 启用数据闭包时，DC 索引、卡片、来源资源、RSU 关联和状态闭合，固定图表契约完整；无数据库模块不创建空 DC 产物。
- 可读文本来源中的 RSU 原文归一化匹配成功。
- 三个契约文件都包含四项固定输入。
- 来源覆盖表存在且没有静默遗漏。
- 未创建 ATP、复杂度表、批次目录或正式测试点产物。

自动校验无法处理的图片、PDF 或外部环境信息必须进入 `pending` 问题和覆盖状态，不能用“脚本无法验证”当作通过理由。

## 12. 常见错误

- 先拆 RSU，后补模块逻辑，导致单元脱离全文背景。
- 把用户讲解只保存在聊天或 Q 表，没有进入 Context Pack。
- 用 AI 改写原子断言替代来源原文，增加新的审核层。
- 把当前需求引用的附件全部展开，忽略人工确认的 L2/L3 范围。
- 把历史 PRD 当成当前需求，恢复未要求的旧功能。
- 在 map 中混入复杂度、验证方式、人工结论和测试步骤。
- 只有资源 ID 没有可点击文件，或链接存在但目标文件不存在。
- 为 Q/FC 创建阅读器不稳定的深层锚点。
- 逐 RSU 生成时只传当前一行，省略全局、模块和模块逻辑基线。
- 用一张模块整库图替代最小数据路径，或给每个 TP 复制关系图，导致上下文噪声和维护漂移。
- 只有表连线，没有完整 Join Predicate、过滤、基数、数据状态、预期推导和清理策略。
- 校验脚本报错后仍宣称产物完成。
- 把前置分析文件平铺在模块根目录，导致它与测试点、方案或用例混放。
