# Data Closure Contract

## 目的

数据闭包用于把一个测试意图涉及的业务数据路径收敛为可追溯、可复用的结构化上下文，使后续测试点能够绑定数据依赖，用例阶段能够据此编写查询、造数、预期推导和清理方案。

它不是只有连线的数据库关系图，也不是按模块复制整库 ER 图。一个模块可以有多张 `DC-*` 卡，每张卡覆盖一条可独立复用的最小业务数据路径；多个 RSU 和测试点可以共享同一张卡，一个测试点也可以引用多张卡。

## 何时创建

满足以下任一条件时创建数据闭包：

- 行为结果取决于数据库中的既有状态、关联关系、过滤条件或聚合口径。
- 被测操作会新增、更新、删除或覆盖数据。
- 后续用例需要通过 SQL 查找数据、准备前置数据、计算动态预期或清理现场。
- API、任务、消息、文件等结果必须与数据库状态做一致性验证。

仅验证静态 UI、纯前端限制、外部系统黑盒结果且不依赖数据库时，不创建空闭包或假关系图，测试点使用 `Data Closure Refs=无`。

## 粒度

按“最小可复用业务数据路径”建卡，不采用以下两个极端：

- 不为整个模块只建一张包含所有表的巨图；无关表会稀释模型注意力，并增加错误连接的概率。
- 不为每个测试点复制一张关系图；这会产生大量重复和版本漂移。

例如“查询纳米数据源球队”可将人工赛事/赛季、数据源赛季映射、纳米比赛/球队、球队映射、当前赛季球队作为一条闭包；同一模块中独立的写入或删除链路应另建闭包。

## 状态

数据闭包索引只允许以下状态：

- `ready`：表角色、连接谓词、过滤条件、数据状态、预期推导及准备/清理结构均已闭合，足以支持测试点和可执行用例设计。环境地址、账号或某个可替换样本值仍可在用例就绪性阶段处理。
- `test-point-ready`：业务语义足以生成正确测试点，但物理字段、可执行查询、造数或清理细节仍有明确缺口；后续用例就绪性必须将缺口闭合或标为 `blocked-input`。
- `blocked`：连接、过滤、数据所有权或业务状态等缺失会改变测试点本身，关联 RSU 必须保持 `pending-context` 或 `pending`，不能继续生成测试点。

状态不是完成百分比。只要缺口会改变测试点语义，就必须使用 `blocked`，不能降级成用例阶段问题。

## 固定索引

启用数据闭包时，map 和 Context Pack 的资源索引都必须登记 `DC-INDEX`；map 还必须登记每张 `DC-xxx` 卡。索引文件固定表头：

```text
DC-ID | 业务数据闭包 | 可点击文件 | 状态 | 关联 RSU | 来源资源
```

## 固定卡片

每张 `DC-xxx` 卡固定包含以下章节：

```text
引用入口
定位
关联范围
闭包目标
输入与输出
关系图
表角色
连接与过滤契约
数据状态与准备契约
查询与断言契约
清理与隔离
当前缺口
```

关系图使用 Mermaid `flowchart`，但图只是导航。以下结构化表格才是生成 SQL 和用例前置条件的主要契约：

```text
方向 | 逻辑对象 | 物理载体/字段 | 约束 | 依据
Table ID | 物理表 | 职责 | 访问模式 | 主键/自然键 | 关键字段 | 数据所有权
Edge ID | From | To | Join Predicate | 基数 | 附加过滤 | 依据
Profile ID | 数据状态目标 | 准备策略 | 预期推导 | 清理策略
用途 | 查询入口 | 断言口径 | 空结果含义 | 依据
```

## 内容要求

- 连接必须写完整谓词，不能只写两个表名或一条箭头。
- 过滤必须覆盖影响结果的来源类型、运动类型、删除状态、租户/中心、时间范围、状态枚举等条件。
- 明确一对一、一对多、多对多或可空关系，以及去重、并集、排序、聚合和空结果语义。
- 表角色必须区分只读来源、关系映射、业务主表、结果表和被测写入目标，并标明数据所有权。
- 数据 Profile 必须描述目标状态、可重复准备方式、动态预期推导和清理策略；不要写“准备测试数据”。
- 查询契约描述查询入口和断言口径；具体环境 SQL、参数值和事务隔离可在用例阶段实例化。
- 关系和过滤只能来自已登记的 schema、SQL、接口、代码、需求或人工确认资源；不能凭命名猜外键。
- 卡片必须把测试点阶段所需的表、字段、连接、过滤、状态和断言语义完整写入固定章节。来源资源是结论证据，不是下游每个 RSU 的递归全文输入；若卡片本身不足以支持测试点，不能用来源链接掩盖缺口。

## 阶段追溯

```text
Schema/SQL/API/代码/人工确认
  -> DC-xxx 数据闭包卡
  -> RSU 相关上下文
  -> 候选及最终 TP 的 Data Closure Refs
  -> 用例的查询、造数、预期推导和清理 SQL
```

测试点生成阶段保留闭包引用，不展开环境相关 SQL。用例就绪性阶段判断闭包是否达到可执行程度；正式用例阶段再按具体环境和数据 Profile 实例化 SQL。

下游输入包对卡片来源资源保留路径、定位用途和正文哈希，以便审计并在来源变化时触发过期，但默认不复制来源全文。某个 RSU 确实需要来源原文时，应在该 RSU 的“相关上下文”中显式引用聚焦资源，而不是让下游从 DC 的引用入口递归推断。
